# IndexNow: tell search engines which pages a deploy changed

The owner, 2026-10-26: "wire IndexNow into the deployment pipeline so that search engines utilizing the protocol (like Bing and Yandex) are notified within minutes whenever new single-purpose utility pages go live."

**Starts when:** every main deploy, by itself: the step "Tell IndexNow engines which pages changed" in `.github/workflows/deploy.yml` runs once a-to-mind.com serves the new deploy. By hand only to look (`--dry-run`) or after a deploy whose step failed.

**What it does:** `tools/indexnow.mjs` diffs the last successful main deploy's commit against this one, maps each changed file to the page it makes (`tools/sitemap.mjs` `pages()` names each page's files; a file in a page's own folder counts for that page, the deepest folder wins, never the home page's folder; the repo's `void.html` is the home page; the `/is-it/` function and skill are every `/is-it/` day), keeps only URLs listed in `void-live-deploy/sitemap.xml`, and POSTs them in one request to `https://api.indexnow.org/indexnow` (`{ host, key, keyLocation, urlList }`, at most 10,000 URLs a request; api.indexnow.org shares them with every IndexNow engine). The key comes from the key file at the site root, `void-live-deploy/<key>.txt` holding the key: public by protocol design (the engine fetches it to check the site is ours), so it is not a secret and never needs rotating.

1. **See what a range would send:** `node tools/indexnow.mjs --base <older sha> --head <newer sha> --dry-run`. No `--base`: every listed page (a first deploy). A new page shows up only when it is in the sitemap: add it where `tools/sitemap.mjs` reads its pages (a tool page in `lib/toolkit.js` TOOLS, a fix page in `tools/fix-pages.json`), run `node tools/sitemap.mjs`, commit both.
2. **Send by hand** (rarely: the deploy does it): the same command without `--dry-run`. Within minutes is the protocol's promise of a fetch, not of ranking.
3. **How to tell it worked:** the deploy log's step prints `IndexNow base: <sha> (head <sha>)`, `IndexNow: N files changed in a..b; K of M listed pages to send`, the URLs, then `IndexNow: 200 OK: URLs submitted (K URLs)` or `202 Accepted: ... the key is still being checked` (the first submissions after a new key). The same line lands in the run summary. A deploy that changed no listed page prints `0 of M listed pages to send` and sends nothing. Bing Webmaster Tools, IndexNow tab, lists what it received.
4. **When an engine says no:** 400 the body is malformed; 403 the key file was not found or does not hold the key (open `https://a-to-mind.com/<key>.txt`: it must answer 200 with the key alone); 422 a URL is not on the host, or the key or keyLocation does not fit; 429 too many requests (the step sends one request per deploy; a burst of deploys can still hit it, and the next deploy's base covers what was missed only if that deploy succeeded, so a 429 page waits for its next change). Each is a warning; the step never fails a deploy (exit 0, `continue-on-error`).

**Mistakes to not repeat:**
- The base is the last *successful* deploy's commit (`gh run list --workflow deploy.yml --branch main --status success`), not `github.event.before`: a deploy that stops for a newer one deploys nothing, and its changes must ride on the next. `github.event.before` is only the fallback.
- The old `tools/indexnow_submit.py` hard-coded two URLs and the key and was run by hand, so new pages never reached the engines. It stays on the salvage shelf; the key lives only in its file now.
- Do not send unchanged pages on every deploy: engines rate-limit sites that resubmit the same URLs (429) and the protocol asks for changed URLs only.
- The sandbox builders work in cannot reach api.indexnow.org; the first real POST is on the runner. Read its log line rather than assuming.
