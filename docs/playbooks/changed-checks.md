# Changed checks: run only the fast checks a change needs

**Starts when:** a builder is about to push (`node tools/finish.mjs` step 6, or by hand), or someone asks why the pre-push check is slow, or why a check that should have run did not (owner, 2026-10-25: six builders on one 4-core box, 3 to 4 minutes of checks each).

**The one rule:** main runs everything (`verify.yml`, `deploy.yml`; `--changed` is ignored in CI). `--changed` only decides what a builder runs before the push, so over-inclusion costs seconds and a wrong skip is caught on main. When in doubt a check is structural (always on).

1. **See what git thinks changed:** `node tools/checks-changed.mjs` lists the files (`git diff --name-only origin/main...HEAD` plus `git status --porcelain`). A stale `origin/main` widens the list: `git fetch origin main` first.
2. **Run the pre-push check:** `VOID_SKIP_BENCH=1 node tools/checks.mjs --changed`. Its first line says how many ran and why the rest were skipped: `--changed: 56 of 428 checks (372 skipped: nothing they cover changed)`. `--full` on finish.mjs, or plain `node tools/checks.mjs`, runs them all.
3. **Why did a check run, or not?** A check runs when it is structural (no test file of its own, or named in `STRUCTURAL` in `tools/checks-changed.mjs`), when its test file changed, when its test imports a changed file (its own `import` lines, one level further, or through `void-live-deploy/skills/deps.json`), when a changed file's basename is in the check's name or its test's name or written in the test, or when void.html, index.html, sw.js, a workflow, package.json or the runner itself changed (then everything runs). The scratch question "what would a change to X run?" is `select()` on the table: see `tools/checks-changed.test.mjs` for the shape.
4. **A check that should have run and did not:** its test reads a file by a path the scan cannot see (a built string, a directory walk). Either import the file, write its name in the test as a literal, or add the check's name to `STRUCTURAL`. Add the case to `tools/checks-changed.test.mjs`.
5. **How to tell it worked:** `node --test tools/checks-changed.test.mjs` passes; the selection line on a one-lib branch names a few dozen checks, not all; the full run on main (`verify.yml`) stays green.

**Learned building it (2026-10-25):** `tools/checks.mjs` runs its checks on import, so the selection had to live in its own module (`tools/checks-changed.mjs`) for a unit test to reach it. 120 tests read a file with `readFileSync` instead of importing it, invisible to an import scan: the literal-name rule covers them. The basename rule over-includes on purpose: a change to `docs/RULES.md` also runs `duel-rules`, `rules-engine` and `merge-rules`, seconds well spent against a wrong skip.
