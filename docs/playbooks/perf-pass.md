# Performance pass: make the page, the 3D or the suite measurably faster

**Starts when:** the owner or Verse says something is slow ("choppy on my phone", "the page takes a while", the suite near its budget), or `tools/page-perf.mjs` shows a number worse than the last pass.

**The one rule:** measure first, change one thing, measure again, put both numbers in the PR. A change with no number is upkeep, not growth (owner, 2026-10-15). Nothing here changes what the page does: an ask answers the same, in the same order.

1. **Measure the page:** `node tools/page-perf.mjs` (desktop) and `node tools/page-perf.mjs --phone --slow` (an older phone on a fair link). It prints the median of 5 loads: first paint, DOMContentLoaded, load, when the modules stopped arriving, requests, compressed bytes, script time, heap. Keep the two lines.
2. **Find what the load pays for that no visitor asked for yet.** Three places pay most: modules imported at load that only one kind of ask needs (`import('/lib/...')` at the top level of the page's script: make them `lazyLib(...)` and warm them on the first key, tap or `?q=`); a skill that statically imports a whole family (`skills/games.js` pulls 29 files, 118 KB compressed, before anyone asks for a game: the biggest remaining lever, but a routing change, so measure the first-ask latency before and after); dead code (a top-level function the file names once is dead: `grep -c` it; take it out and shelve it in `docs/SALVAGE.md`, never silently).
3. **The 3D:** `node tools/test_void.mjs --only "3d: low-poly"` prints each miniature's median frame time full and low-poly on the emulated phone; `fresh({ phone: true })` in `tools/test_3d.mjs` is the phone. Pixels are what a phone runs short of: the pixel ratio (`MAX_DPR`, `REGRESS_DPR`), shadow passes (`shadowDraws`) and re-meshing tiers (`DETAIL`) are the knobs, the governor (`governStep`) turns them on its own.
4. **The suite:** it runs on main as three shards at once (`verify.yml` matrix, `node tools/test_void.mjs --shard i/3`: each section goes to the shard its heading hashes to, `tools/shard.mjs`; `--list --shard i/3` shows a shard's sections, and the two local shards of 2 took 872 s and 1,117 s where the whole suite took 1,187 s). A section too slow for its shard is still a section to make faster: `VOID_TRACE=1 node tools/test_void.mjs 2> trace.txt` writes one line per check with the second it finished; the run's end prints "slow N s before: <check>". A `waitForTimeout` longer than 1 s that waits for something observable becomes `until(...)`; a page opened twice for one check is opened once. Never skip, loosen or quarantine a check to save time.
5. **Check what you changed, nothing more:** the browser sections you touched (`--only "<heading words>"`), `VOID_SKIP_BENCH=1 node tools/checks.mjs`, then step 1 again. Copy `void.html` to its two deploy copies after any edit (`cp void.html void-live-deploy/void.html void-live-deploy/index.html`).
6. **Ship** with both numbers in the PR and in the ledger line, and what you measured but left alone and why.

**Mistakes already made (2026-10-16):** The worst one: four PRs were built by restoring whole files from a stash taken at the start of the session (`git checkout stash@{0} -- <file>`), so every line other builders had added to those files since then read to git as a deletion and was dropped on merge, with no conflict (main lost the cook-flow chip, seven test registrations and eight suite sections; #8xx put them back). Branch from a freshly fetched main and carry your edits as a patch (`git diff <base> <your tree> -- <file> | git apply --3way`), never as a whole file, and before pushing compare each touched file against main for lines that only vanished. warming the lazy libs on `focusin` warmed them on every load (the ask box autofocuses), so the saving was zero on desktop: warm on a key, a tap or a `?q=` link, never on focus. Measuring while the browser suite runs skews both. `encodedDataLength` is 0 for a module Chromium served from its memory cache: count requests, trust bytes only for a cold load.
