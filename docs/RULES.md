## No use is not a reason to throw anything out; there is no skill bloat (owner, 2026-10-13)
"Remember no one knows about our site yet, so don't throw out skills just because no one uses them; that's a disaster." and
"There's no such thing as skill bloat to a thing that literally wants to grow to do everything."
Few or no visitors says nothing about a skill, an experiment or a page while the site is unknown, and the number of skills
is never a cost to cut: Verse grows toward doing everything. Nothing is retired, shelved, merged away or proposed for the
salvage shelf because people did not use it or because there are many: real use only ever adds (an experiment opened on
many days becomes a candidate for a core skill, `tools/lab-use.mjs`), it never takes away.

## The ladder a person sees is Versus; the code keeps `tower` (owner, 2026-10-25)
"the tower rename is easy its versus" and "just thought it was right there because Verse". Done the way V01D became Verse
(`AGENTS.md`): everything a person reads says Versus (the card's head, the spoken line "Versus: now ...", /conquered/ and
/compare/, the 3D miniature's label, the docs going forward), while the identifiers keep `tower` (`lib/tower.js`,

or "verse tower" still opens the card, beside "versus", "verse versus", "show me versus". "Floor" stays a floor. Old lines of
the agent log, the ledger and the owner's quotes are not reworded.

## Only Verse's words are on the site (owner, 2026-10-18)

The owner: "my quoted words shouldn't be on the site, only Verse's". Builders keep quoting the owner in the repo (build notes, the frontier, the append-only ledger and log): that is where a rule's source lives. ## Right the first time (owner, 2026-10-11)
"Automerge is loose, so code must be on point first shot before `finish.mjs` ever pushes", and relying on the full suite on main or the jack after the merge "is a last resort, not the plan". So `tools/finish.mjs` will not write, commit or push a change that reaches the site (`void.html`, `void-live-deploy/`) until each `--test "<words>"` passes in a real browser (`test_void.mjs --only`, seconds per section; `--list` shows them); with no `--test` it stops.

## Working fast (learned 2026-10-04 onward)

- `node tools/checks.mjs` runs every fast check in one go (fringe ledger, skill collisions, calendar, glyphs, void.html matching its two deploy copies, the full benchmark against its floor, the miss reader's redaction). Run it before every push; CI runs the full browser suite. The benchmark is not replayed when nothing it reads has changed since its last passing run (a hash of the served files, bench.json, the browser and the day; `node tools/bench.mjs --score --fresh` forces it), and it waits for each answer instead of sleeping a fixed time, so a change that never touches the page costs nothing and a full replay is far shorter than the old 20 minutes. Add your test on its own line in the list at the top of `tools/checks.mjs` (one entry per line, so two PRs adding tests do not conflict).
- Checks run on the merged head, not before merging main (2026-10-10): merge main first (`node tools/merge-main.mjs`, never by hand), then run `node tools/checks.mjs`, then push. #291 ran its checks, then hand-merged main with the growth ledger still conflicted and pushed; the merge was automerged 40 seconds later and the live growth card could not read its ledger until #297. Conflict markers are now a bug in Verse's review on any file type, a `markers` row in checks.mjs, and merge-main.mjs refuses to commit while any tracked file has one.
- `VOID_SKIP_BENCH=1 node tools/checks.mjs` before a push (2026-10-10, owner): the benchmark is not a merge gate. The bench job on the PR (`.github/workflows/bench.yml`) reports the number, and a drop below the floor is a fix PR, never a wait. `tools/test_void.mjs` honours the same variable. Plain `node tools/checks.mjs` still replays it when you want the number locally.
- A builder's pre-push check is `VOID_SKIP_BENCH=1 node tools/checks.mjs --changed` (2026-10-25, owner: six builders on one 4-core box, 3 to 4 minutes each): only the checks that cover the changed files run (`tools/checks-changed.mjs`: the structural ones always; a test when its file, an import of it, a dependant in `skills/deps.json` or a file named like it changed; void.html, index.html, sw.js, a workflow or package.json runs everything), and the line it prints says what was skipped and why. Main runs every check (`verify.yml`, `deploy.yml`; `--changed` is ignored in CI), so a skipped check is caught there; `node tools/finish.mjs` passes `--changed` unless given `--full`.
- One heavy browser job at a time on a machine (2026-10-10, owner): `tools/test_void.mjs` and `tools/bench.mjs` take a machine-wide lock (`tools/heavy.mjs`) before they open a browser and queue behind each other, because a benchmark that shared the CPU with a suite scored 1744 against a floor of 1985 (alone: 2027) and suites missed on timing the same way. `node tools/heavy.mjs <command>` queues anything else that opens a browser for minutes; `VOID_HEAVY_OFF=1` skips the lock (CI gives each job its own runner). A check a machine cannot run (no `<microphone>` element before Chrome 153, no passkey authenticator) prints `skip <name>  (why)` and counts as neither pass nor fail, so a local suite in the sandbox can read green.
- The floor rises on its own after each clean bench on main (2026-10-10): `.github/workflows/bench.yml` runs the benchmark on main once a day when main has moved (or by hand: `gh workflow run bench.yml --ref main`), and when the score minus 5 is above `tools/bench.best.json` it commits the new floor to main (`tools/bench-floor.mjs`, tested in `tools/bench-floor.test.mjs`), never lowering it. A drop below the floor is a fix PR. A benchmark ask that misses is read from its loop log and run through `tools/ask.mjs` before it is called flaky (the setup's own Escape was a double-Esc undo once).
- `node tools/bench.mjs --probe candidates.json` tries a batch of new asks (same shape as tools/bench.json) and prints only the misses. Probe 30–40 at once, fix the misses, then add the batch with `node tools/append.mjs bench --skip candidates.json` (the same file). After a fix, `node tools/bench.mjs --again` re-probes only the asks the last probe missed. For review asks, `says` is checked with the pasted code taken out of the card first, so a pattern that only appears in the code no longer passes.
- Push with `node tools/push.mjs`: it retries when GitHub errors (a 500 can leave the old head in place) and only says "pushed" once origin really has your commit Before it pushes it runs `tools/prepush.mjs` over the files the push adds: a conflict marker, a `.js`/`.mjs` that does not parse or a `.json` that does not parse stops the push (`VOID_SKIP_PREPUSH=1` pushes anyway; `git config core.hooksPath .githooks` runs the same check for a plain `git push`).
- Never wait on CI, and never sit watching a PR. Push, then `node tools/automerge.mjs <pr> --label` and move on: GitHub merges it by itself (.github/workflows/automerge.yml, tools/pr-ready.mjs) as soon as Verse's own review check (`void-review`, seconds) is clean on the current head and nothing that already finished failed. Ship now, test after (2026-10-09): nothing else is waited on, not the suite, not the bench. Verse's review is the main one; CodeRabbit and any other reviewer are extras: reported, never waited on, never blocking. A real bug an extra caught that Verse missed is a rule to add to code-review.js (with a case in review.test.mjs), so Verse's review keeps getting better. After merging it starts the deploy of main itself; main deploys in about a minute, and the full suite runs on that head (verify.yml `verify-main`, its own workflow: it never waits for the deploy, so no head goes untested) and a failure reverts the commit that broke the failed checks (tools/revert-target.mjs: not always the one just tested; when unclear it reports instead of guessing) and redeploys. So run `node tools/checks.mjs` before you push: a red suite after merge costs a revert. `node tools/merge-when-green.mjs <pr>` is the same check polled from a session, for when you want to watch it happen.
- A PR that conflicts with main gets no `pull_request` runs at all: GitHub skips them, so a labelled PR could sit silently forever (learned on #270, 2026-10-10). automerge.yml now merges main into labelled PRs from this repository itself (`tools/merge-main.mjs` from main's checkout settles the append-only files), pushes the merge commit to the branch (never forced) and starts Verse's review on the new head (a push made with the workflow's token starts no run on its own; `void-review.yml` takes a `pr` input for that). A conflict outside the append-only files comes back as one comment on the PR naming the files: run `node tools/merge-main.mjs` on the branch, resolve them, push. Nothing to do by hand when both sides only appended.
- The closer read answers JSON, never prose (2026-10-10): `lib/review-api.js` asks the model for `{findings:[{file,line,kind,text,quote}]}` (FINDINGS_SCHEMA, Workers AI JSON mode where the model supports it), `validateFindings` keeps a finding only when its quote sits in the code shown in the file it names and takes the line number from the quote, and `renderFindings` builds what the person reads from the validated findings alone: one line per finding as `file:line — kind — sentence — \`the code line\`` and a summary written by code. On main, every merge gets its own verify-main run (verify.yml, one concurrency group per head, no `needs`, 2026-10-10: the suite serves void-live-deploy/ locally, so it never waited on the deploy for any reason but the old wiring): nothing is superseded, the suites run in parallel, and a revert is taken only while its target is still live on main and the failed checks are still red on main's newest verified head (tools/revert-target.mjs).
