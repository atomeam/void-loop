## B.I.T.E. on every run (owner, 2026-10-11)

From a video the owner shared on building with Claude Code: **Brief** (who it is for, the problem, what the first version does, and what it will not build), **Implement** the smallest useful piece, **Test** it the way it will be used, **Evolve** from what the test showed. ## Working fast (learned 2026-10-04 onward)

- `node tools/checks.mjs` runs every fast check in one go (fringe ledger, skill collisions, calendar, glyphs, void.html matching its two deploy copies, the full benchmark against its floor, the miss reader's redaction). Run it before every push; CI runs the full browser suite. The benchmark is not replayed when nothing it reads has changed since its last passing run (a hash of the served files, bench.json, the browser and the day; `node tools/bench.mjs --score --fresh` forces it), and it waits for each answer instead of sleeping a fixed time, so a change that never touches the page costs nothing and a full replay is far shorter than the old 20 minutes. Add your test on its own line in the list at the top of `tools/checks.mjs` (one entry per line, so two PRs adding tests do not conflict).
- Checks run on the merged head, not before merging main (2026-10-10): merge main first (`node tools/merge-main.mjs`, never by hand), then run `node tools/checks.mjs`, then push. #291 ran its checks, then hand-merged main with the growth ledger still conflicted and pushed; the merge was automerged 40 seconds later and the live growth card could not read its ledger until #297. Conflict markers are now a bug in Void's review on any file type, a `markers` row in checks.mjs, and merge-main.mjs refuses to commit while any tracked file has one.
- `VOID_SKIP_BENCH=1 node tools/checks.mjs` before a push (2026-10-10, owner): the benchmark is not a merge gate. The bench job on the PR (`.github/workflows/bench.yml`) reports the number, and a drop below the floor is a fix PR, never a wait. `tools/test_void.mjs` honours the same variable. Plain `node tools/checks.mjs` still replays it when you want the number locally.
- One heavy browser job at a time on a machine (2026-10-10, owner): `tools/test_void.mjs` and `tools/bench.mjs` take a machine-wide lock (`tools/heavy.mjs`) before they open a browser and queue behind each other, because a benchmark that shared the CPU with a suite scored 1744 against a floor of 1985 (alone: 2027) and suites missed on timing the same way. `node tools/heavy.mjs <command>` queues anything else that opens a browser for minutes; `VOID_HEAVY_OFF=1` skips the lock (CI gives each job its own runner). A check a machine cannot run (no `<microphone>` element before Chrome 153, no passkey authenticator) prints `skip <name>  (why)` and counts as neither pass nor fail, so a local suite in the sandbox can read green.
- The floor rises on its own after each clean bench on main (2026-10-10): `.github/workflows/bench.yml` runs the benchmark on main once a day when main has moved (or by hand: `gh workflow run bench.yml --ref main`), and when the score minus 5 is above `tools/bench.best.json` it commits the new floor to main (`tools/bench-floor.mjs`, tested in `tools/bench-floor.test.mjs`), never lowering it. A drop below the floor is a fix PR. A benchmark ask that misses is read from its loop log and run through `tools/ask.mjs` before it is called flaky (the setup's own Escape was a double-Esc undo once).
- `node tools/bench.mjs --probe candidates.json` tries a batch of new asks (same shape as tools/bench.json) and prints only the misses. Probe 30–40 at once, fix the misses, then add the batch with `node tools/append.mjs bench --skip candidates.json` (the same file). After a fix, `node tools/bench.mjs --again` re-probes only the asks the last probe missed. For review asks, `says` is checked with the pasted code taken out of the card first, so a pattern that only appears in the code no longer passes.
- Push with `node tools/push.mjs`: it retries when GitHub errors (a 500 can leave the old head in place) and only says "pushed" once origin really has your commit Before it pushes it runs `tools/prepush.mjs` over the files the push adds: a conflict marker, a `.js`/`.mjs` that does not parse or a `.json` that does not parse stops the push (`VOID_SKIP_PREPUSH=1` pushes anyway; `git config core.hooksPath .githooks` runs the same check for a plain `git push`).
- Never wait on CI, and never sit watching a PR. Push, then `node tools/automerge.mjs <pr> --label` and move on: GitHub merges it by itself (.github/workflows/automerge.yml, tools/pr-ready.mjs) as soon as Void's own review check (`void-review`, seconds) is clean on the current head and nothing that already finished failed. Ship now, test after (2026-10-09): nothing else is waited on, not the suite, not the bench. Void's review is the main one; CodeRabbit and any other reviewer are extras: reported, never waited on, never blocking. A real bug an extra caught that Void missed is a rule to add to code-review.js (with a case in review.test.mjs), so Void's review keeps getting better. After merging it starts the deploy of main itself; main deploys in about a minute, and the full suite runs on that head (verify.yml `verify-main`, its own workflow: it never waits for the deploy, so no head goes untested) and a failure reverts the commit that broke the failed checks (tools/revert-target.mjs: not always the one just tested; when unclear it reports instead of guessing) and redeploys. So run `node tools/checks.mjs` before you push: a red suite after merge costs a revert. `node tools/merge-when-green.mjs <pr>` is the same check polled from a session, for when you want to watch it happen.
- A PR that conflicts with main gets no `pull_request` runs at all: GitHub skips them, so a labelled PR could sit silently forever (learned on #270, 2026-10-10). automerge.yml now merges main into labelled PRs from this repository itself (`tools/merge-main.mjs` from main's checkout settles the append-only files), pushes the merge commit to the branch (never forced) and starts Void's review on the new head (a push made with the workflow's token starts no run on its own; `void-review.yml` takes a `pr` input for that). A conflict outside the append-only files comes back as one comment on the PR naming the files: run `node tools/merge-main.mjs` on the branch, resolve them, push. Nothing to do by hand when both sides only appended.
- The closer read answers JSON, never prose (2026-10-10): `lib/review-api.js` asks the model for `{findings:[{file,line,kind,text,quote}]}` (FINDINGS_SCHEMA, Workers AI JSON mode where the model supports it), `validateFindings` keeps a finding only when its quote sits in the code shown in the file it names and takes the line number from the quote, and `renderFindings` builds what the person reads from the validated findings alone: one line per finding as `file:line — kind — sentence — \`the code line\`` and a summary written by code. Nothing parseable means "Nothing to report on a closer read". Every false claim it made on 2026-10-10 was about code it had not seen; a free model followed a text shape only half the time (it echoed the placeholder, ignored the list, wrote prose), so the prose channel is gone structurally. `parseFinding`/`quoteCheck` stay as a second layer. `/api/review` answers `quoted: { kept, dropped, parsed, echoes }` and the PR footer says so. `tools/review-learn.mjs` reads the rendered lines back, counts paragraphs with no claim under `empty`, and `void-review.yml` can be dispatched with `report_only` to print the closer read of a merged PR in the log without posting (it runs main's tools, so the footer is current on any PR). When no closer read comes back, the PR footer says only `closer read unavailable (access|model|network)`; the exact reason is in the Pages function log (`wrangler pages deployment tail`), never in a public comment, ledger or log line.
- A new push to a PR cancels the older run of that PR (deploy.yml: the per-PR concurrency group with cancel-in-progress); on a PR the benchmark runs as its own job, in parallel with the suite. On main, every merge gets its own verify-main run (verify.yml, one concurrency group per head, no `needs`, 2026-10-10: the suite serves void-live-deploy/ locally, so it never waited on the deploy for any reason but the old wiring): nothing is superseded, the suites run in parallel, and a revert is taken only while its target is still live on main and the failed checks are still red on main's newest verified head (tools/revert-target.mjs).
- What a run builds (2026-10-08): first read Void's own asks (`node tools/reflect.mjs`, mirrored at the top of `domains/void.voice.md`) and weigh them heavily: a concrete ask from Void gets built next, and the agent log line and commit say "asked by Void". Then real misses (`node tools/misses.mjs`), then an open inbox row, then the top unfinished Next item. Ship one useful skill or a real improvement to one, and add bench asks only for the behaviour you changed. Asks invented to fill the bench no longer count as progress: run 47 added 23 and all passed on the first probe. If none of those is actionable, take the top unclaimed item in `domains/void.frontier.md` (2026-10-09: "we should not sit still"): ship its smallest visible piece and write the next step on it. A run never ends on "no work found".
- A run that ships a new skill, miniature, workflow or secret adds one line to `docs/MAP.md` in the same PR, so the map does not go stale between rewrites (2026-10-10; the last full rewrite was four days late).
- Everyday maths and unit asks now pass on the first probe (run 36: 32 of 32), so spend probes where Void is thinner: review asks in more languages, places and times, words and definitions, and phrasings people actually type. `bench.mjs --probe` skips asks the bench already has.
- `node tools/ask.mjs "ask" …` shows what Void answers for each ask (who answered, the card text, any page error such as a TDZ crash) with outside services blocked. Use it when a probe misses for no clear reason.
- Every new unauthenticated POST endpoint gets one hostile read before its label: ask "what could a stranger make this do?" (queue jobs, spend model budget, write rows, send anything) and add the limit or check that answers it.
- Void reviews code, and it reviews every PR first. `void-live-deploy/lib/code-review.js` holds the checks (bugs, risks, style, safe automatic fixes) the site runs when someone asks "review this code", and `tools/review.test.mjs` tests them, including a speed budget (a regex that backtracked once made one file take minutes). `node tools/review-pr.mjs [--base origin/main] [--gate]` runs them on the lines a branch adds in about a second; run it before pushing. The `void-review` check (.github/workflows/void-review.yml) posts the review and fails while the added lines carry a bug or a risk: fix it, or mark a line that is right as written with a `void-review: ok` comment. A skill's place in the routing order is one file in `void-live-deploy/skills/order/`, `<rank>-<name>` like `0480-watch`; a new skill adds its own file at a rank between its neighbours, then `node tools/skills-index.mjs --write` rewrites the index. `node tools/checks.mjs` fails (`index` row) while the index is stale; a skill the index lists by hand (a branch from before the order files) gets its file at that place with `node tools/skills-index.mjs --adopt`, which `tools/merge-main.mjs` also runs when a merge conflicts on the index before regenerating it.

- `node tools/draft-check.mjs [draft.html]` opens fringe drafts headless (by default the ones this branch changes) and fails on a missing noindex, a page error on load or first button press, anything fetched from outside, or no `window.__name` hook. checks.mjs runs it, so there is no need to hand-write a test script for a new draft. Give the draft's hook a `selftest()` that runs its maths on made-up data and returns true (or a string saying what is wrong); draft-check calls it, so the maths is checked on every run.

Never link node_modules into it: a linked node_modules got committed once, and copying that commit back replaced the real folder with a link to itself. checks.mjs fails if git tracks anything under node_modules.
- The bench says when it was disturbed (2026-10-10): after the parallel run it replays every miss by itself (up to 100). A miss that passes alone was load and is counted as answered (`loadMisses` in the result); a miss that still misses alone is real and listed in `wrong`, whatever the latency says. A run with any load miss prints `inconclusive: machine under load (p95 Xms vs baseline Yms; N of M misses passed alone); re-run alone`, and an inconclusive run never writes `bench.last.json`, the pass cache, the floor or the baseline. `bench.mjs` exits 1 only when the real misses take the score below the floor (`tools/bench.best.json`); `checks.mjs` shows `inconclusive` for a run that is otherwise at the floor, and the bench action runs it once more and then reports it. The latency baseline (`latency.local` / `latency.ci`, each `{p50, p95, n, cores, pages, sha, at}`, rule in the file's note) is a diagnosis, not the verdict: it only tightens, from a conclusive run at the floor, and only a run with the same number of pages is compared to it. Default pages are cores - 1 (at most 6). See `tools/bench-load.mjs`, `tools/bench-floor.mjs`.
